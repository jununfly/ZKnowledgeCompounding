## 节点 `1-1-2`

### 1-1-2 · D1 · Q2 · 为什么要删除（触发动机）？

**A（逐字）**

```text
zj 2026-11-16 原话：两者都要。完整考虑如下：1、防止已经腐化的节点被误用，污染各种运行时上下文的知识有效性和可信度；2、节约复审注意力；3、删除对应的是「已经明确无用了，真要用到能接受一次重新摄入的成本」，归档对应的是「日常用不到，但很小概率需要查阅时它还在」。以删除的方式精简掉，既有运行时的效率收益，也有存储空间的节约。
```

**Note（逐字）**

```text
结论：动机同时取两点——①防腐化节点污染运行时上下文（新增，此前未知，待查事实）②节约复审注意力（version_seq=60 实锤）；且第 3 点给出删除/归档的语义边界：删除=明确无用+可接受重摄入成本，归档=小概率仍需查阅故保留。zj 明确「两者都要」，不只选其一。
```

## 节点 `1-1-5`

### 1-1-5 · D1 · Q5 · TTL 时长与起算点（多久不恢复才真删）

**A（逐字）**

```text
zj 2026-11-16 原话：TTL 时长 = 7天；起算点 = 墓碑时刻；定期跑扫描，但 daily 的周期太短，软删除已经可以保证 动机 1（污染）+ 2（复审注意力），可以设置按月扫描。
```

**Note（逐字）**

```text
结论：TTL=7d 从 is_delete=1 时刻起算；扫描按月（非 daily）——理由是软删除已即时满足动机1+2，真删无时效压力。注意时序：7d TTL + 月度扫描 → 实际真删发生在墓碑后第 7~37 天（取决于扫描日），非精确第 7 天；此延迟被 zj 接受（因软删除已屏蔽污染/复审）。每日 daily driver 仍跑软删除可见性，月度扫描只做「墓碑满 7d → 真删」的批量清理；不注册系统级调度（硬约束），按月触发点挂现有入口（方案设计阶段定）。
```
