# MVP 交付形态 = 本地 web 应用

Status: accepted (2026-10-31, zj 拍板)

PRD 与架构全文从未指定交付形态（PRD 只有「界面」两字，架构 §9 项 ⑦ / §10 项 7 明写「待最小垂直切片排期时确定」）。MVP 却有三处不可替代的交互——每日复审队列（列表 + 三态标注 + 收口埋点）、蒸馏 HITL（LangGraph interrupt 后人工编辑结构化 claim 再 resume）、5 度量面板——三者全是「列表 + 表单 + 编辑」。我们决定交付 **本地 web 应用（FastAPI + 服务端渲染极简页，`localhost:8000`）**，并明确**不做**打包、签名、对外分发、桌面壳、TUI。

## Considered Options

- **本地 web（采纳）**：一次覆盖三处交互；蒸馏 HITL 要编辑 claim 文本 + evidence 引用 + topic，这是每天都要走的链路，编辑体验决定外生锚能否持续产生。代价是多一层 HTTP/模板栈，与「依赖最少」原则有张力。
- **TUI（Textual）**：终端内启动快、更贴合「本地/离线/轻量」，但长文本编辑与后续度量图会撞墙，而复审队列是每日高频动作。
- **CLI 为主 + 最小 web 只做复审队列**：两处形态并存，HITL 编辑仍落在 CLI 的痛点上。
- **桌面壳（Tauri/Electron）**：MVP 阶段纯负担（打包/签名/更新），对核心命题零信息。

## Consequences

- 架构 §6.5.1 的硬前提被满足：`pushed/completed/queue_remaining/labeled_completed` 有真实载体每日写入。若不做这个界面，budget 估计器永远停在 `confidence='none'`、L3 闸门无样本，**两个闭环皆为装饰**——这是选 web 而非轻量的真正理由，不是交互偏好。
- 「上线」被重新定义为**单人 dogfood**：zj 本人用导入的真实历史素材跑通 e2e 闭环 ≥7 个活跃日。对外分发不属 MVP，推迟到 P6 之后另议。
- 新增风险 R10（外生锚供给）：该判定要求 zj 真的每天打开它 ≥7 天；若 P6 第 5 天仍未达 3 个活跃日，启用降级判定「累计 ≥20 个复审动作」。
